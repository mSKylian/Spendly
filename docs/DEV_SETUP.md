# Local dev setup — server credentials

The Express server (`server.ts`) uses the Firebase Admin SDK to reach Firestore for
`/api/analyze`, `/api/scan-receipt`, `/api/parse-statement`, and `/api/admin/*`.

The Admin SDK needs Google credentials. Without them, every one of those endpoints
returns **503 Service Unavailable** (`Could not load the default credentials`),
while the client-side Firebase SDK keeps working — which is exactly the confusing
"app works but API calls fail" symptom.

## Providing credentials (pick one)

1. **Application Default Credentials (recommended for dev)**

   ```bash
   brew install --cask google-cloud-sdk
   gcloud auth application-default login
   gcloud auth application-default set-quota-project spendly-dev-21016
   ```

   Sign in with the Google account that owns the dev Firebase project
   (`VITE_FIREBASE_PROJECT_ID` in `.env`).

2. **Service account key file**

   Firebase console → Project settings → Service accounts → Generate new private key,
   save the JSON outside the repo, then:

   ```bash
   export GOOGLE_APPLICATION_CREDENTIALS=/path/to/service-account.json
   ```

After either option, restart the dev server. On startup it now runs a Firestore
connectivity probe and logs whether credentials are working.

## Docker credentials

For Compose, generate a Firebase service-account JSON in Firebase Console
(*Project settings → Service accounts*) and save it outside the repository. Set
its absolute host path in `.env`:

```env
FIREBASE_SERVICE_ACCOUNT_FILE="/home/kylian/.config/spendly/firebase-admin.json"
```

Then start Compose with the optional credentials override:

```bash
docker compose -f compose.yaml -f compose.firebase-admin.yaml up -d --build
docker compose logs -f
```

The JSON is mounted read-only at runtime and excluded from Git and the image
build context. Never paste it into `.env`, commit it, or send it in chat.

## Bootstrap the first admin

Invitations can only be generated by an existing admin. To bootstrap the first
one, open Firebase Authentication, copy your own user's UID, then create a
Firestore document at `admins/<UID>` in the same project. The document only
needs to exist; the server uses its document ID for the role check. Once Docker
logs `Firestore connectivity OK`, sign in again and the admin endpoints can
read that role and generate invitations.

## Admin endpoints

`/api/admin/*` additionally require an `admins/{uid}` document in Firestore for
your signed-in user, otherwise they return 403.
